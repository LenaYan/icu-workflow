# Session: 病理 AI 产品对比 + ICU 医生 AI 病理/知识库工作流建议
Date: 2026-06-01

## Background / Context

用户（ICU 主治）连续提出两个问题：

1. 横向对比六款病理诊断 AI 产品（Paige PanCancer / PathAI / Lunit SCOPE / 透彻影像 ThorouGood / 迪英加 / 兰丁 LBP），从收费、开源、功能维度做排名与分析
2. 作为以临床为主的重症医生，如何把 AI 接入日常"病理诊断 + 知识库建设"工作流

会话目的是建立"哪些是病理科产品、哪些才是 ICU 医生自己能落地的"清晰边界，并把 KB 架构与 Obsidian + Claude Code 现有 setup 对接。

---

## Key Decisions

- **病理切片级 AI（Paige / 透彻等）不属于 ICU 医生直接落地的工具**——属于病理科 + 数字病理 scanner + 三类证的范畴。ICU 端只需要"看懂他们的输出 + 临床整合"。
- ICU 医生的 AI-病理工作流定位在 **L1 层 = LLM 辅助病理报告解读 + clinico-pathologic correlation**，而非 L2 层 WSI 阅片。
- 知识库建设沿用现有 `cases/ literature/ guidelines/ research/ snippets/` 五目录结构，但要分成 **L1 原子层 / L2 综合层 / L3 应用层** 三层语义。
- 文献笔记必须加 **YAML frontmatter**（trial / year / journal / pico / verdict / tags），让 Claude 可 grep 检索。
- 所有 AI 输出的临床建议必须带 **`[evidence: TRIAL/指南章节]`** 引用尾标，无来源不接受。
- PHI 安全：处理真实病理报告前必须本地脱敏后再丢给云端 LLM；含 PHI 内容禁止外发。

## Generated Plan / Solution

### Part 1 — 六款病理 AI 产品对比与排名

**横向对比表**

| 产品 | 厂商/国别 | 核心功能 | 监管最高资质 | 收费模式 | 开源? |
|---|---|---|---|---|---|
| Paige PanCancer / Paige Prostate | Paige.AI (MSK 衍生，US) | 前列腺癌检出、PanCancer Detect、淋巴结转移、乳腺 | **FDA De Novo (2021)** + CE-IVDR | SaaS + per-slide，估 $10–50/slide | ❌ 闭源；底层 Virchow / Virchow2 在 HuggingFace 公开 (non-commercial) |
| PathAI AISight / PathExplore | PathAI (US) | 数字病理平台、TME 量化、NASH-CRN、IHC 量化、pharma biomarker | CE-IVD（部分）+ RUO/LDT；PathAI Diagnostics 走 CLIA LDT | Pharma/CRO 合作为主；医院端订阅 | ❌ 闭源 |
| Lunit SCOPE PD-L1 / HER2 / IO | Lunit (韩国，KOSDAQ) | IHC 定量（PD-L1 TPS/CPS、HER2）、TIL、IO biomarker | CE-IVD, 韩国 MFDS；AstraZeneca / Guardant 合作 | Pharma license + 医院 SaaS | ❌ 闭源 |
| 透彻影像 ThorouCyte / ThorouPath | 北京透彻未来 (CN) | 宫颈 TCT（核心）、胃/结直肠活检 WSI 诊断 | **NMPA 三类证 (2022)** —— 国内首张病理 AI 三类 | 按检测量计费，估 ¥10–50/例 | ❌ 闭源 |
| 迪英加 D-PAS | 杭州迪英加 (CN) | 数字病理平台 + 宫颈 TCT、HER2、PD-L1、Ki67、HP、ALK 多模块 | NMPA 三类证（宫颈 TCT，2023）+ 多个二类 | 平台 + 模块授权 / 按例 | ❌ 闭源 |
| 兰丁 LBP / CytoBrain | 武汉兰丁智能 (CN，港股 2138.HK) | 宫颈 LBP/TCT 细胞学筛查 + 云端 AI 阅片中心 | NMPA 注册证（细胞学辅助） | "AI 阅片中心"代检，按例 ¥20–50 | ❌ 闭源 |

**综合排名（ICU/科研合作 + 临床落地视角）**

- 🥇 第一梯队：**Paige.AI**（FDA + Virchow2 权重学术可用）、**Lunit SCOPE**（IO/biomarker 一枝独秀）
- 🥈 第二梯队：**透彻影像**（国内首张三类证 + 高分发表）、**迪英加**（产品线最全 + 平台型）
- 🥉 第三梯队：**PathAI**（深度强但医院端落地弱）、**兰丁**（公卫筛查规模化但技术较前一代）

**场景适配**

| 场景 | 首选 | 备选 |
|---|---|---|
| 科研合作 / foundation model 二次训练 | Paige (Virchow2) | Lunit |
| 国内三甲临床落地（拿证、可计费） | 透彻 | 迪英加 |
| IO/biomarker 临床试验 | Lunit SCOPE PD-L1 | PathAI |
| 公卫/基层宫颈筛查项目 | 兰丁 | 透彻/迪英加 TCT 模块 |
| 数字病理整体平台采购 | 迪英加 D-PAS | PathAI AISight（非中国市场） |

**关键判断**

- 没有真正"开源"的临床级病理 AI；最接近开源的科研基础模型是 Virchow/Virchow2、UNI (Mahmood Lab, *Nature Medicine* 2024)、CONCH、Prov-GigaPath (Microsoft/Providence, *Nature* 2024)
- 收费几乎全部不公开标价，per-slide / per-case 是行业惯例
- 学术验证密度（PubMed 2024–2025）：Paige > Lunit ≈ PathAI > 透彻 > 迪英加 > 兰丁

### Part 2 — ICU 医生 AI 病理诊断 + 知识库建设建议

#### 0. 定位先纠偏

| 层次 | 工具 | ICU 医生能否落地 |
|---|---|---|
| L1 — 病理报告 / 图像的**临床整合** | LLM (Claude/GPT) + 多模态 | ✅ 现在就能 |
| L2 — 全切片 AI 辅助诊断 | Paige / 透彻等 | ❌ 是病理科的事 |

#### 1. ICU 端"AI + 病理"的真实高频场景

| 场景 | 痛点 | AI 工作流 |
|---|---|---|
| Endomyocardial biopsy（心脏移植排斥 ISHLT 分级、心肌炎） | 报告读懂但临床意义模糊 | 报告 PDF + 临床信息 → LLM 解读 + 治疗调整 |
| Open lung biopsy in undifferentiated ARDS（DAD vs OP vs DAH vs eosinophilic） | 病理 vs 临床/影像对不上 | 三角验证：病理 + HRCT + BAL → 鉴别支持/反对点 |
| Renal biopsy in ICU AKI（lupus nephritis、AAV、TMA） | ISN/RPS 分类与免疫抑制方案对应 | 报告 + 血清学 → 分类 + KDIGO/EULAR 治疗路径 |
| Autopsy / 床旁尸检 | 报告滞后、与生前诊断对照少 | 生前问题列表 + 尸检报告 → clinicopathologic correlation |
| HLH / 噬血 | 骨髓 + sCD25 + ferritin 综合判断 | HScore / HLH-2004 自动核对 + 鉴别 |

实操：在 `cases/_templates/` 加一个 `pathology-integration.md` 模板，强制把【病理报告原文 / 临床问题 / 影像 / 实验室】四栏并列。

#### 2. 知识库三层架构

```
L1 - 原子层 (atomic notes)
  literature/notes/  → 一篇文献一个 note（PICO + 结果 + 批判 + 临床影响）
  guidelines/        → 一条指南一个 note（推荐 + 证据级别 + 来源段落）

L2 - 综合层 (synthesis / MOC)
  literature/topics/ → 如 "ARDS-ventilation.md" 汇总十几个 RCT 结论矩阵
  guidelines/_compare/ → SSC 2021 vs ESICM 2023 对照表

L3 - 应用层 (action)
  cases/             → 真实病例 → 反向引用 L1/L2
  snippets/          → 床旁速查
```

**AI 友好约定**

1. 每个原子笔记顶部加 YAML frontmatter：
   ```yaml
   ---
   trial: PROSEVA
   year: 2013
   journal: NEJM
   pico: severe ARDS / prone ≥16h / supine / 28d mortality
   verdict: positive
   tags: [ards, prone, ventilation]
   ---
   ```
2. 统一引用格式 `**TRIAL_NAME (Journal Year)**`
3. `literature/topics/` 用矩阵表：一行一个 trial，列 = PICO + 关键结果 + 偏倚来源
4. 明确 reasoning trace：临床建议旁标 `[L1: PROSEVA]` 或 `[L2: ARDS-ventilation§3]`

#### 3. 推荐工具栈（按优先级）

| 工具 | 用途 | 必要性 |
|---|---|---|
| Obsidian + Claude Code（现有） | 主战场，文件即数据 | 已有 ✅ |
| Claude 多模态 (Sonnet/Opus 4.x) | 读病理报告 PDF + 影像 + 实验室单 | ⭐⭐⭐ 必要 |
| NotebookLM (Google) | SSC/ESICM/BTF PDF 全文问答 | ⭐⭐⭐ 强烈推荐，免费、长上下文、引用精准 |
| Zotero + Better BibTeX | 文献管理，导出 markdown 到 `literature/notes/` | ⭐⭐ 推荐 |
| 本地 RAG (PrivateGPT / Open WebUI + Ollama) | 含 PHI 内容不能上云时 | ⭐ 按需 |
| 病理切片 AI（Paige/透彻等） | ❌ 不要自己折腾，等病理科上 | — |

#### 4. 红线 / 容易踩的坑

1. **PHI 不上云**：处理真实病理报告前先在本地脱敏；`cases/README.md` 规则要严格执行
2. **不要让 AI 输出"绝对化诊断"**：所有 AI 建议必须以 `[evidence: TRIAL/指南章节]` 收尾——这条建议写进 `CLAUDE.md` 第 6 节"工作约定"
3. **小心 RCT 时效性**：LLM 知识截止日期之后的关键试验（ESETTLE、PHIND、ARREST-2 等）需要自己补进 `literature/notes/`
4. **KB 不是单向写入**：每月 1–2 小时反向 review，让 Claude 帮跑一遍 `literature/topics/`，看结论是否需要更新
